# Contributing to MINT

Thank you for your interest! Issues, ideas and pull requests are welcome.

## Reporting a problem

Please include:

- the MINT version (shown in the sidebar, or `mint/version.py`), your OS and Python version;
- the output of `python check_install.py` — it contains no keys;
- what you did, what you expected and what happened.

Never attach confidential documents, knowledge bases, `.env` files or `feedback.jsonl` from real use: they can
contain your organisation's data. Security issues: see [docs/SECURITY.md](docs/SECURITY.md).

## Development setup

```bash
git clone https://github.com/Sdorenskiy/mint.git && cd mint
./install.sh                 # or install.bat on Windows
python tests/run_all.py      # about 10 s, no network or models needed
```

The tests simulate the LLM gateway and generate test documents on the fly, so you do not need model access
to work on MINT. To try the real interface without a gateway, use Ollama ([docs/OLLAMA.md](docs/OLLAMA.md)).

## Code layout and rules

- `mint/` is the core and must not import Streamlit; everything Streamlit-specific lives in `mint/ui/`.
  This keeps the core usable from scripts (`eval_search.py`, `kb_stats.py`) and testable without a browser:
  the quality check, for example, lives in `mint/evaluation.py`, and `mint/ui/quality.py` only draws it. A whole
  scenario is one core function — `answer_question()`, `run_audit()`, `verify_remarks()`; a tab only collects
  input, shows progress (`on_progress`) and renders the result.
- Module dependencies go one way (see the docstring in `mint/__init__.py`); avoid import cycles.
- Settings: connection data in `.env`, behaviour in `config.yaml` (`mint/config.py`). Values derived from model
  limits are computed in `mint/limits.py`.
- New behaviour needs a test. Unit and integration checks go into `tests/test_app.py` or a new
  `tests/test_*.py` registered in `tests/run_all.py`; mark sections by kind (`[unit]`, integration,
  end-to-end).
- `python tests/run_all.py` must pass. GitHub Actions runs it on Linux (Python 3.10–3.12) and Windows for
  every pull request.
- Keep code compatible with Python 3.10 (for example, no nested quotes of the same kind inside f-strings).

## Language

- Identifiers are in English. Comments and docstrings are currently mostly in Russian. New code may use
  English comments, and translations of existing ones are welcome.
- **User-visible text** is written in Russian in the code and wrapped in `tr()`:
  `tr("Файл {name} загружен", name=name)`. Add the English translation to `mint/i18n/en.py` with the same
  `{placeholders}`. Module-level constants are marked with `N_()` and translated where they are shown:
  `tr(CONSTANT)`. `tests/test_i18n.py` fails if a translation is missing or stale.
- **Prompts** — every text the model receives — live in `mint/prompts/ru.yaml` and `en.yaml`: one key per
  text, `{{name}}` placeholders filled by the code (`render()`), the language follows the interface. Both files
  must have the same keys, placeholders and number of rules; `tests/test_prompts.py` checks this and that the
  answer format the code parses (severity tags, JSON codes, `[Source: …]`) is still in the prompts. If you
  change one language, change the other. Measure a change with the quality check with chat answers, before and
  after: the prompt version in the results tells the runs apart. Users' own edits are a separate layer
  (`prompts.yaml`, the "📝 Prompts" page) and never change these files. A key users may edit is listed in
  `EDITABLE` (`mint/prompts/__init__.py`); if the code parses part of its answer, list that part in
  `FORMAT_PARTS`, so an edit that drops it is not applied. A new key that is not in `EDITABLE` is markup and is
  shown read-only.
- Log messages and `kb_stats.py` are still in Russian. `eval_search.py` writes its report in the interface
  language (`MINT_LANG` or `--lang`).
- Documentation exists in English (`README.md`, `docs/`) and Russian (`README.ru.md`, `docs/ru/`). If you
  change one, update the other or mention it in the pull request so it can be synced.

## Diagrams

The diagrams (`MINT_architecture`, `MINT_engineering`) are generated by `tools/diagrams/`: English versions in
`docs/`, Russian ones in `docs/ru/`. The text is written in Russian in the scripts; the English translation of
every label is in `tools/diagrams/en.py`. Change the script (and `en.py`), not the `.excalidraw` file, then
rebuild both languages and the previews:

```bash
cd tools/diagrams
python build_engineering.py ../../docs/ru/MINT_engineering
python build_engineering.py ../../docs/MINT_engineering --lang en
python render.py ../../docs/MINT_engineering.excalidraw ../../docs/MINT_engineering_preview.png 0.35
python render.py ../../docs/ru/MINT_engineering.excalidraw ../../docs/ru/MINT_engineering_preview.png 0.35
```

The English build stops and lists the labels that have no translation in `en.py`. `tests/test_diagrams.py`
fails if a diagram differs from its script, `en.py` has translations for labels that no longer exist, a diagram
names a function or parameter that no longer exists, or shows parameter values that differ from what the code
computes.

## Interface

- The look lives in `mint/ui/assets/mint.css`, HTML pieces (header, verdict stamp, sources) in `mint/ui/theme.py`.
  Nothing may be loaded from the internet: MINT runs in closed networks. Fonts and images go into `static/`.
- Motion answers a user action or marks the one moment on load; every animation must end in a usable state
  when `prefers-reduced-motion` turns it off.
- Streamlit renames its `data-testid` attributes between versions. `tools/ui_preview/run_preview.py` takes
  screenshots on real Streamlit and dumps the markup of the elements the theme targets (`dom.txt`). GitHub
  Actions runs it for `feat/ui-*` and `feat/eval-*` branches (workflow "UI preview") and pushes the result to the
  `ui-preview-<branch>` branch.

## Pull requests

- Keep a pull request focused on one change.
- Describe what changed, why, and how you tested it.
- Add a line to `CHANGELOG.md` under "Unreleased".
- Never commit `.env`, `config.yaml`, `glossary.json`, documents (`*.docx`), knowledge bases or logs.
  `.gitignore` covers these, but please double-check.
