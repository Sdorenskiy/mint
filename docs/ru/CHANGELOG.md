# Изменения MINT

[English](../../CHANGELOG.md) · **Русский**

## 21.1 — установка с первого раза, без PyTorch, архитектурный профиль по умолчанию

- **Установка с первого раза.** `install.sh` / `install.bat` ставят точные версии пакетов из `requirements.lock`
  (один файл для Linux, Windows и macOS). GitHub проверяет их при каждом изменении и каждую ночь: установка с нуля
  на Ubuntu (Python 3.10–3.12), Debian 12 без `python3-venv` (как Astra Linux 1.8) и Windows, затем разбор .docx
  настоящим Docling, база → чат → аудит и самопроверка со страницей на настоящем Streamlit
  (`.github/workflows/install.yml`, `tests/test_real_install.py`). Типовые затруднения скрипты решают сами:
  неполную `.venv` от прерванной установки создают заново; без `python3-venv` pip скачивает системный pip
  (администратор не нужен); если точной версии нет на зеркале — ставят по `requirements.txt`; `--clean` — с нуля.
  Самопроверка подсказывает `./install.sh --clean`, если стоят не проверенные пакеты.
- **Без PyTorch.** .docx разбирает бэкенд Word из Docling — напрямую, а не через общий конвертер Docling, который
  подгружает и разбор PDF с моделями. Результат тот же, что у полного Docling, — это сверяется на GitHub на тестовых
  документах Docling и примерах MINT; на своих документах — `tools/docx_parity.py`. Установка — 72 пакета, ≈ 0,6 ГБ
  на диске и ≈ 165 МБ скачивания вместо 122 пакетов, 2,1 ГБ и 540 МБ, без библиотек моделей (PyTorch,
  transformers, huggingface_hub, OpenCV). Заодно исправлено `No module named 'torch'` / `'docling_parse'` при
  загрузке .docx после установки с нуля. Docling закреплён на 2.127.0. Установка с PyTorch продолжает работать;
  убрать его — `./install.sh --clean`.
- **Профиль «Архитектура и ИТ-решения» — по умолчанию**: промпты те же, что до профилей (версия набора
  `ru-8fd10871` / `en-9c3500f7`). Универсальный — в боковой панели или `profile: general` в `config.yaml`.
  `tools/review_stats.py` считает аудиты без профиля архитектурными.
- **Чат: уточнённый вопрос больше не заменяет ваш.** Вопрос, переписанный по истории диалога, раньше искался один
  — и если при переписывании терялся термин, сокращение или номер, поиск уходил не туда. Теперь поиск идёт по обоим
  вопросам: кандидаты сливаются, реранкер берёт лучший из двух баллов. Переписывание, отличающееся только регистром
  и знаками, не показывается; подпись — «Искал по вашему вопросу и по уточнённому с учётом диалога». Промпты не
  менялись.

## 21.0 — сохранённые аудиты, разбор замечаний экспертом, обновление на месте

Версия для передачи MINT коллегам: эксперты разбирают замечания, и по их отметкам видно, что улучшать.

- **Профили** — наборы промптов для чата, аудита и контроля исправлений (боковая панель → «🧭 Профиль», `profile` в
  `config.yaml`). **«Архитектура и ИТ-решения»** — промпты MINT до появления профилей слово в слово: роли
  Архитектурного комитета, архитектурные критерии аудита; версия набора промптов та же, что раньше (это проверяет
  тест), — результаты сравнимы. **«Универсальный — любые документы»** (по умолчанию): нейтральные роли («ведущий
  эксперт-аудитор документов», «ведущий эксперт-консультант по базе знаний»), критерии для любого документа —
  требования и обязанности, полнота, согласованность с документами-основаниями и нормами, цифры, даты и ссылки,
  скрытые риски; правила проверки те же. Фраза чата «информации нет» в нём — «В предоставленных документах…»
  (узнаются фразы обоих профилей). Профиль заполняет поле «Общие критерии проверки», тексты профилей — на странице
  «📝 Промпты». Профиль сохраняется с каждым аудитом, `tools/review_stats.py` добавляет разбивку по профилям.
  **Чтобы всё работало как раньше, укажите `profile: architecture`.**
- **Сохранённые аудиты** («📂 Мои аудиты» в начале вкладки аудита): каждый аудит сохраняется на компьютере
  пользователя, в `LOG_DIR/audits/<id>` — заключение, лог, сырые ответы модели (сжаты), копия проверенного .docx и
  разбор эксперта. Аудит открывается без повторной загрузки документа, его можно удалить. Перепроверка
  непроверенных разделов пишет в ту же папку, разбор остаётся.
- **Разбор замечаний экспертом** (блок «✍️ Разбор замечаний экспертом» под заключением): все замечания в порядке
  заключения — основные по разделам, ответы на пункты, не подтверждённые, мелкие, опечатки — с номером в
  заключении, проверкой, которая нашла замечание, «⭐ в «Главном»», «📎 по документу-основанию», числом нашедших
  проверок и цитатой; отметка ✅ беру / ➖ мелочь / ❌ неверно с причиной из списка и комментарием; таблица своих
  замечаний, которых MINT не нашёл. Отметки сохраняются сразу и привязаны к тексту замечания — перепроверка их не
  сбивает. По 15 замечаний на странице, фильтр по блокам, «➡️ К неразмеченным».
- **«Мои замечания»**: отмеченные ✅ (по желанию и ➖) и свои — в Word (таблица: №, раздел, замечание,
  критичность), в Markdown или примечаниями Word в проверенном документе.
- **Файл разбора для улучшения MINT** (`mint-review/1`): один аудит («📤 Скачать разбор (.json)») или все аудиты с
  разбором («📥 Скачать разборы (.jsonl)» в «📂 Мои аудиты»). По умолчанию с текстами замечаний; «Без текстов
  замечаний» оставляет только виды проверок, критичность, отметки и причины — без текстов, цитат, разделов,
  комментариев и имён файлов. `tools/review_stats.py` сводит много файлов в Markdown: доля верных замечаний по
  видам проверок, блокам заключения, критичности, «Главному», документам-основаниям, моделям; причины «неверно»;
  сколько замечаний эксперты добавили сами; примеры текстов.
- **Обновление на месте**: `update.sh` / `update.bat` берут новую версию (.zip или папку), заменяют папки с кодом
  целиком, сохраняют `.env`, `config.yaml`, `glossary.json`, `checklists.yaml`, `prompts.yaml`, `.venv`, базу и
  логи (даже если в архиве есть свои) и запускают `install.sh` (с офлайн-комплектом, если он есть в новой
  версии). Версия MINT — внизу боковой панели.
- **Памятка для пользователей** — [QUICK_GUIDE.md](QUICK_GUIDE.md): запуск, аудит, разбор замечаний, передача
  разборов, обновление.
- `docs/ru/SECURITY.md`: в «Что и где хранится» добавлены `LOG_DIR/audits/` и файл разбора.
- **Документы-основания — исправления после прогона на настоящем руководстве по ИБ** (два ТЗ по шифрам; Qwen 27B
  при обоих ТЗ, выбранных вручную, нашла 0 и 2 частично из 20 замечаний эталона):
  - по названию документ базы больше не совпадает своими собственными ссылками: руководство или пояснительная
    записка, разработанные по тому же ТЗ («разработан в соответствии с … Техническое задание …»), не принимаются
    за само ТЗ. Шифр ищется дальше в начале документа базы (лист утверждения), но не в его «Ссылочных документах»;
  - фрагменты к разделу: в проверки на деле попадал почти только один из двух ТЗ (147 фрагментов против 19), и в
    основном перечень сокращений и общие разделы требований — у них общие
    слова с любым разделом. Теперь разделы сокращений, терминов и содержания не берутся, оценка по словам не
    поднимает длинные перечни, добавлена близость по смыслу (векторы самой базы, один эмбеддинг на раздел), и
    каждому документу-основанию — равная доля `audit_basis_max_chars`;
  - в логе видно, что MINT нашёл сам и как, что добавлено и что снято вручную: раньше всё, что прошло через блок на
    вкладке, называлось «выбран вручную».

- **Повторы в кусках одного длинного раздела**: таблица на десятки строк проверяется кусками, и модель пишет об
  одном недостатке в каждом куске своими словами (на руководстве по ИБ — около 10 раз об одном и
  том же). Замечания из разных кусков одного раздела теперь склеиваются без модели
  при совпадении слов от 40 % вместо 80 %; замечания одного ответа не склеиваются никогда. В логе — сколько.

- **Документы-основания** (`audit_basis_docs`, `audit_basis_max_chars`, блок «📎 Документы-основания» на вкладке
  аудита): MINT берёт ссылки документа на его основание — с титула («разработан в соответствии с … Техническое
  задание на развитие (шифр)») и из «Ссылочных документов» — ищет их в базе знаний по шифру (в начале документа
  базы; документ, который на шифр только ссылается, не в счёт) или по названию и добавляет их фрагменты, ближайшие к
  разделу, в каждую проверку раздела и в ответы на пункты отдельным блоком «документ должен им соответствовать». На
  руководстве по ИБ с 20 эталонными замечаниями Qwen 27B без подсказки нашёл 1 из 20; с «особым вниманием», которое
  принесло требования ТЗ в каждую проверку, — 5 и 2 частично: требование, касающееся всего документа (куда
  передаются данные), в разделе написано другими словами, и поиск по тексту раздела его не находит. Теперь это
  происходит без подсказки. В блоке видно, что найдено и по какой ссылке и чего нет в базе; документ можно снять или
  добавить. В логе — строка «Документы-основания».

- **Меньше ложных замечаний проверок без модели** на технических документах (руководство по ИБ с большими таблицами
  серверов и правил межсетевого взаимодействия): (1) сокращения — части имён серверов, учётных записей и путей
  («CORP\\Admins», «srv.CORP.local»), коды документов («…ТЗ.2»), названия продуктов («Astra Linux SE»), слова заглавными
  буквами, которые есть в тексте и обычным написанием («НЕТ», «ТЕСТ», «ВАЖНО»), и общеизвестные в ИТ (SSH, NTP, TLS,
  TCP/UDP, БД, ОС …) больше не считаются сокращениями без расшифровки; (2) содержание и заголовки — «Приложение А»,
  которое добавляет нумерация Word, и подписи таблиц в содержании больше не дают «разделов нет»; (3) пустые колонки
  таблиц — строки «Зона …» на всю ширину и пустая колонка «№» больше не делают заполненные колонки «пустыми»; (4)
  тип документа для чек-листа берётся из названия (короткая строка или ячейка таблицы, не в кавычках), а не из
  ссылки на другой документ вроде «… Техническое задание на развитие» или «на основании технического задания …».

- **Глубокая проверка узнаёт процесс, описанный без таблицы**: раньше вопросы о каждой паре шагов, каждом требовании
  к процессу и границах процесса задавались, только если процесс оформлен таблицей операций. Теперь шаги берутся и
  из списка (нумерованного, абзацев «Шаг 1. …» или маркированного после вводной фразы вроде «Обмен выполняется в
  следующем порядке:»), и из подразделов «Шаг N». Списки требований («… должен …»), участников, терминов и короткие
  перечни названий процессом не считаются. В шапке лога — какие описания процесса найдены («„2.1 Порядок обмена“ —
  список, шагов: 4»), а если не найдено — где MINT их искал. В промптах вопросов о процессе «таблица операций»
  заменена на «шаги процесса».

- **Схемы — по текущему коду** (архитектурная и инженерная, RU и EN): в аудите — проходы 2–3, ответы на «особое
  внимание» и чек-лист после остальных проверок и с их замечаниями, сведение повторов без слияния разных шагов
  процесса, «Главное», рассуждения для аудита и сырые ответы модели; черновик карточки системы — в потоке базы
  знаний, отдельным рядом панели 8 (mint/cards.py), в таблице особенностей компании и в таблице нагрузки на сервисы;
  блок «⚙️ Настройки аудита», MINT_CHECKLISTS и общая пауза при HTTP 429.

- **Черновик карточки системы по базе знаний** (боковая панель → «📌 Для аудита» → «🗂️ Собрать черновик карточки
  системы по базе»): MINT задаёт базе по узкому вопросу на каждый раздел карточки — названия, назначение, сервисы,
  лимиты, защита данных, хранение, планы, ограничения, подключение, требования к смежникам — и собирает черновик по
  шаблону карточки: только найденное, у каждого факта источник, «нет в базе» — где сведений нет, «проверьте» — где
  ссылка не ведёт на найденный фрагмент. Скачивается в .md; эксперт проверяет, дописывает ограничения и планы и
  загружает карточку в базу. Работает с любой моделью и любой базой; промпт правится в «📝 Промпты».

- **Сведение повторов не сливает разные шаги процесса**: на прогоне DeepSeek глубокая проверка трижды нашла «на
  шаге 3 получатель не может прочитать файл, зашифрованный на чужой сертификат» (переходы 1 → 2, 2 → 3, 3 → 4), а
  сведение повторов слило все замечания о шифровании в одно — о шаге 4 → 5, и замечание эталона потерялось (так уже
  бывало раньше). Теперь замечания, у которых в начале указаны разные шаги без общего («шаг 2 → шаг 3» и «шаг 4 → шаг
  5»), не сводятся — ни моделью, ни склейкой по словам; в логе они «отдельно (другой шаг процесса)». Промпт сведения
  говорит о том же, но модель это правило нарушала — теперь его держит код.

- **Строка «Сейчас» под «⚙️ Настройки аудита»** показывает и сведение повторов, и рассуждения — так же, как шапка
  лога («выключены», «как настроено на сервере», «включены для аудита»): выключенное сведение повторов или
  рассуждения видно до запуска, а не только по логу.

- **«Весь документ одним запросом» вместе с глубокой проверкой**: утверждения для сверки противоречий и опечатки
  теперь ищутся по разделам, как в обычном режиме; раньше в этом режиме — одним вопросом на весь документ (и
  опечаток из него бралось не больше шести).

- **Ответ на пункт без тегов критичности**: на прогоне DeepSeek модель ответила на пункт «особого внимания»
  списком из десятка замечаний, но без тегов [СРЕДНИЙ] — MINT склеил их в один абзац ответа, и замечаниями они не
  считались (не сводились с другими, не попадали в документ с примечаниями). Теперь, если тегов в ответе нет совсем,
  пункты списка после строки «Ответ:» — замечания средней критичности. Проверка оформления пишет яснее: «Пункты
  оформлены обычным текстом, а не заголовком: …» — сверка с эталоном считала прежнюю формулировку («их нет в
  структуре») замечанием об отсутствии пункта.

- **Эмбеддинги снова пачками**: с доработки «Аудит без шума» запрос пачки текстов к модели эмбеддингов падал в
  коде MINT (лишние строки от ответа потоком) и молча заменялся запросами по одному тексту — загрузка документов в
  базу и подбор норм шли во столько раз медленнее, каков размер пачки (`embed_batch_size`). Результаты от этого не
  менялись; теперь пачка — один запрос.

- **Все настройки аудита в одном месте**: блок «⚙️ Настройки аудита» на вкладке аудита — база знаний, глубокая
  проверка, весь документ одним запросом, самокритика (была в основных настройках боковой панели), сведение
  повторов, «Главное», системы, проходы, рассуждения, параллельность, лимиты и объёмы контекста. Под блоком — что
  сейчас включено; в «Экспертных настройках» боковой панели аудита больше нет.

- **«Главное» в начале заключения** (`audit_summary_max`, по умолчанию 12): модель-редактор выбирает самые важные
  замечания — разрывы и ошибки процесса, противоречия, несходящиеся цифры, нарушения норм — и пишет суть каждого
  одной строкой со ссылкой на номер ниже («→ №14», «→ особое внимание 2, №1»). Это указатель, а не копия: число
  замечаний и сверка с эталоном не меняются. Модель не ответила — берутся найденные несколькими проверками и
  критичные.

- **Несколько проходов** (`audit_passes`, 1–3): проверка разделов и вопросы глубокой проверки о процессе,
  требованиях, цифрах и противоречиях повторяются с температурой не ниже 0,4; замечания проходов сводятся вместе,
  у замечания — «найдено: 3 (проверок — 2, проходов — 2)». Случайный пропуск одного прохода восполняет другой, а
  найденное несколько раз выше в заключении. В логе — что дал каждый проход.

- **Аудит с рассуждениями** (`audit_reasoning`): модель рассуждает перед каждым ответом аудита, даже если
  рассуждения выключены для чата; к длине ответа — 6000 токенов на рассуждения, таймаут не меньше 300 с. В логе
  видно, рассуждала ли модель на самом деле.

- **Ответы на «особое внимание» согласуются с остальными проверками**: на прогоне Qwen ответ на пункт был «нет,
  проблем нет» — по догадкам модели, — хотя другие проверки нашли по этой теме два замечания. Теперь ответы на
  пункты идут после проверки разделов и глубокой проверки и получают их замечания: ответ должен с ними
  согласовываться, повторять их не нужно. «Проблем нет» — только с дословной цитатой документа; если документ
  этого не говорит — «из документа не ясно» и что не описано. То же для чек-листа: «да» не противоречит найденному.

- **Самокритика не удаляет пробелы процесса**: на том же прогоне она удалила замечания о том, как файл попадает
  из одной системы в другую, как «детали реализации» и по предположению о назначении систем. Теперь замечания о
  том, кто выполняет шаг, через какую систему передаются данные и может ли получатель их прочитать, так не
  удаляются; удалять замечание можно, только если его опровергают текст документа или нормы.

- **Сырые ответы модели**: на вкладке аудита рядом с логом — «📥 Скачать сырые ответы модели». В файле каждый
  запрос аудита, перепроверки и сверки с эталоном: какая проверка спросила (часть документа, вопрос глубокой
  проверки, пункт «особого внимания», сведение повторов, сверка), сколько шёл ответ, что спросили (начало и
  конец запроса; документ целиком — пометкой) и что модель ответила — слово в слово, до разбора на замечания.
  Нужен, чтобы разобрать спорный случай: видно, ошиблась модель или MINT, разбирая её ответ.

- **JSON с переносами строк — не зацикливание**: Qwen пишет ответ-JSON с отступами, и строка «"verdict":
  "НАЙДЕНО",» повторяется у каждого объекта — защита от зацикливания обрывала такой ответ на третьем повторе и
  вырезала повторы: в сверке с эталоном у пунктов 3–6 пропали вердикты, 7–9 не пришли вовсе. Короткие поля JSON
  («ключ: короткое значение») за повтор больше не считаются; одинаковые замечания или объекты целиком — по-прежнему
  зацикливание. Сверка: вердикт в любом виде («✅ найдено», «Не найдено», «Partially», «Да»); пункты без ответа
  или с непонятным вердиктом переспрашиваются пачками по 3; в ошибке — какие пункты не сверены и почему.

- **Другие модели (прогон на Qwen 27B)**: ответы разбираются, как бы модель их ни оформила:
  - замечание без «-» в начале, с тегом после метки («шаг 3 → шаг 4: [СРЕДНИЙ] …»), и любой перевод строки
    (\r, разделитель строк Unicode) — отдельное замечание; раньше такие склеивались с предыдущим (на Qwen — 5 из
    40 ответов глубокой проверки);
  - JSON из ответа модели: лишний текст со скобками до и после, висячие запятые, объекты без массива и оборванный
    ответ (берутся целые объекты);
  - сверка с эталоном: если ответ на весь эталон не разобран, эталон сверяется пачками по 3 пункта; если не
    разобран и так — в ошибке видно начало ответа модели. На Qwen сверка не выполнялась совсем («ответ модели не
    разобран»), хотя все 9 замечаний эталона в логе аудита были.

- **Шлюз просит реже (HTTP 429)**: раньше MINT ждал 2–5 с и не слушал Retry-After, остальные потоки продолжали
  слать запросы, а повтор в конце аудита шёл сразу и с одной попыткой — на настоящем прогоне так не выполнились
  16 из 34 вопросов глубокой проверки и сведение повторов. Теперь пауза общая для всех потоков — сколько просит
  шлюз (Retry-After), иначе 5, 10, 20 с (не больше 60); на 429 — не меньше 4 попыток при любом `llm_retries`;
  в логе аудита — сколько раз шлюз просил реже и сколько длились паузы.

- **Шапка при свёрнутой боковой панели**: Streamlit делает свою верхнюю полосу непрозрачной, и заголовок MINT
  уходил под неё наполовину; теперь страница начинается ниже полосы. В предпросмотре интерфейса — сценарий
  «панель свёрнута» с проверкой, что шапка не заходит под полосу.

- **Аудит точнее** (по трём прогонам глубокой проверки на настоящих ФТ: все 8 важных замечаний модель находит
  каждый раз, но среди 150–240 замечаний за прогон к ним относятся 27–40):
  - вопрос о переходе между шагами: модель писала по замечанию на каждый из 4 вопросов промпта — на каждый
    переход; теперь — не больше двух проблем именно этого перехода, без общих для всех шагов (контроль формата,
    сроки, сбои), вопрос «куда девается результат» — только если следующий шаг его не использует; лимиты по видам
    вопросов (`DEEP_KIND_MAX`): переход — 2, требование — 2, границы — 3, противоречия — 2, сверх лимита — в логе;
  - проверка раздела, «особое внимание» и самокритика: пожелание «не указаны требования к …» — замечание, только
    если этого требует сам документ или норма из базы;
  - противоречия — только об одном и том же предмете; замечание, которое последней фразой само говорит «проблем
    нет» / «противоречий не выявлено», в заключение не попадает (в логе — сколько таких убрано);
  - внутри раздела заключения сначала замечания, которые нашли несколько проверок независимо (с пометкой «нашли
    проверок: N»), затем по критичности;
  - в логе — состав каждой группы сведения повторов: что осталось, что влилось, что оставлено отдельно;
  - опечатки: «ошибок нет» убирается и у фраз длиннее 200 символов.

- **Сведение повторов без потерь**: на настоящих ФТ после сведения пропали два эталонных замечания, хотя модель
  их нашла — модель объединила замечания одного вопроса глубокой проверки о разных проблемах одного шага, а
  опечатку — с другими опечатками раздела, и в заключении осталась одна формулировка из группы. Теперь замечания из
  одного ответа модели (одна часть документа, один вопрос глубокой проверки, один пункт «особого внимания») друг с
  другом не сливаются; опечатки модели на сведение не передаются — повтор опечатки определяется по исправляемой
  фразе, а строки, где «как правильно» совпадает с «как написано» и модель сама пишет «ошибки нет», убираются.
  В промпте сведения: одно место документа — ещё не повод объединять замечания с разными вопросами к нему.

- **Универсальное заключение**: главные замечания — по разделам документа, в его порядке, вместо постоянных тем
  «Информационная безопасность», «Функциональные требования», «SLA», «Архитектура»; в заголовках заключения и
  матрицы контроля нет «архитектурного комитета»; самокритика не просит тему. Меньше шума: проверка раздела просит
  не больше 10 существенных замечаний (было 20 — модель заполняла лимит), а замечание, которое начинается с пункта
  другой части документа, отсеивается — на настоящих ФТ первая часть (титульный лист, содержание, сокращения) дала
  19 замечаний, 15 из них про 2.2.3 и раздел 4. Раздел замечания определяется по пункту в его начале. Проверки
  оформления: строки содержания и шапки таблиц жирным больше не дают ложного «нет в содержании» и звёздочек в
  названиях колонок.

- **Знания эксперта в аудите** — то, чего документ сам о себе не знает:
  - чек-листы по типам документов: тип узнаётся по словам в имени файла и в начале документа (или выбирается
    вручную); каждый пункт — вопрос по всему документу с ответом «да / частично / нет / не относится» и замечаниями,
    в заключении — блок «Чек-лист»; пункты правятся на вкладке аудита и сохраняются в свой `checklists.yaml` (вне
    git; образец — `checklists.example.yaml`);
  - документы базы с отметкой «📌 Учитывать в аудите всегда» (правила экспертов): модель получает их в каждой
    проверке сверх норм поиска — целиком или ближайшими фрагментами (`audit_pinned_max_chars`);
  - карточки систем («🗂️»): карточка подключается к проверке раздела, где система упоминается (названия — из
    строки «Названия:» и заголовка, с окончаниями); по каждой системе, упомянутой не меньше двух раз, модель
    выписывает, что документ от неё требует: есть, в планах, нужна доработка, противоречие, неясно (`audit_systems`);
  - ответы на «особое внимание», чек-лист и вопросы о системах идут параллельно (`audit_parallel`); ползунок
    называется «Аудит: запросов к модели одновременно».

- **Аудит без шума** (по прогону глубокой проверки на настоящих ФТ: 9 из 9 эталонных замечаний найдено, но около
  300 замечаний в заключении, одна часть зациклилась на 420 одинаковых строк, а шлюз не соблюдал лимит длины):
  - ответы в аудите — потоком: MINT сам обрывает ответ далеко за лимитом длины или зациклившийся (`llm_stream`);
    шлюз без потока получает обычный запрос и это запоминается;
  - одинаковые строки внутри ответа отбрасываются, из ответа берётся не больше 25 замечаний (узкий вопрос — 6,
    «особое внимание» — 10, весь документ — 40), сначала критичные;
  - самокритика — пачками по 15, сведение повторов — пачками: раньше на длинном списке оба молча не работали;
  - в заключении сначала главное; мелкие и общие (низкие, без цитаты и места) и опечатки — отдельными блоками;
  - разделы проверяются параллельно (`audit_parallel`); в логе — время аудита по часам и сумма по разделам;
  - замечание по норме заканчивается ссылкой [Источник: файл, раздел], ссылка на файл, которого модель не
    получала, — в «Не подтверждено»;
  - сверка с эталоном строже (общее замечание не засчитывается за конкретное) и показывает, сколько всего
    замечаний в заключении и сколько из них относятся к эталону;
  - весь документ одним запросом: нормы ищутся по каждому разделу, а не по титульному листу; ответ — не больше
    четверти окна модели; подпись в ходе аудита — без «до 4500 симв.».

- **Глубокая проверка аудита** (`audit_deep`, по умолчанию вкл.) — чтобы не только сильная модель находила
  разрывы в процессе и противоречия. Проверка разложена на узкие вопросы, на которые надёжно отвечает и модель
  среднего размера:
  - процесс: код находит таблицы операций; вопросы по каждой паре соседних шагов (откуда вход, кто передаёт, может ли
    получатель прочитать данные — шифрование на чей сертификат), по каждому требованию к процессу (есть ли шаг, нет ли
    противоречия), по границам процесса (начало, конец, результат каждому потребителю);
  - противоречия: модель выписывает утверждения частей с темой из закрытого списка, утверждения одной темы
    сравниваются (и внутри раздела);
  - цифры: показатели выписывает и пересчитывает программа (сутки × 365 против года, среднее и максимум), модель
    оценивает готовые расчёты;
  - опечатки — по каждой части.
  Вопросы идут параллельно (`audit_parallel`, по умолчанию 3), их не больше `audit_deep_max_calls` (60): первыми —
  процесс и цифры. Не полученные из-за сбоя шлюза — повторяются вместе с непроверенными разделами.
- **Оформление без модели:** пункт, оформленный текстом вместо заголовка; содержание против заголовков; пустые
  таблицы, колонки и поля; шаг таблицы операций без исполнителя, сервиса, входа или результата; пустой раздел.
- **Весь документ одним запросом** (галочка на вкладке, для сравнения): одна проверка — документ целиком, ответ до
  4000 токенов, таймаут не меньше 300 с; не помещается в окно — проверка по разделам с предупреждением.
- **Сверка с эталоном** под заключением: ожидаемые замечания → какие нашла выбранная модель (найдено, частично,
  нет), таблица для скачивания. Так сравниваются модели и настройки на одном документе.

- **Аудит: меньше повторов, ложных «не описано» и выдуманных ссылок.** Разобран отчёт по настоящим
  функциональным требованиям (14 частей, из 72 замечаний около 20 — повторы, обрывки и следы нарезки; ключевое
  замечание по процессу пропущено).
  - Части — по разделам документа: заголовок со своим текстом и таблицами; раздел до 1,5 лимита части не режется
    (таблица процесса — целиком со своим заголовком); продолжение большой таблицы помечено. Таблицы после Docling
    сжимаются — выравнивание пробелами удваивало документ. Настоящие ФТ: 6 частей вместо 14.
  - Документ целиком — в каждой проверке раздела и в самокритике, если помещается в окно модели
    (`audit_full_document`); иначе — оглавление, а замечания «не описано» сверяются с другими разделами. Каждая часть
    знает своё место в документе. Правило «пройди процесс по шагам» в проверке раздела.
  - «Особое внимание»: один ответ на каждый пункт по всему документу (строка «Ответ:» и замечания) — отдельным
    блоком заключения. Раньше на пункт отвечала каждая часть, и части без процесса писали «процесс не описан».
  - Без модели: сокращения без расшифровки и расшифрованные, но неиспользуемые; ссылки на таблицы, пункты и акты
    и цифры в замечаниях, которых нет ни в документе, ни в нормах, — в блок «Не подтверждено источником».
  - Подпункт замечания («сроки и этапы перехода;») остаётся в своём замечании, а не становится отдельным.
  - Повторы сводит модель (+1 вызов, `audit_merge_duplicates`); у замечания — раздел документа.
  - Ответы на «особое внимание», которые модель не дала, повторяются вместе с непроверенными разделами.
- **Окно модели «типовое значение»** (32768) — подсказка в README: сервер окна не сообщил, задайте его вручную.

- **Таймауты в аудите.** Разделы, на которых модель не ответила (таймаут, перегрузка шлюза, сеть), проверяются
  ещё раз в конце аудита с бо́льшим таймаутом (вдвое больше настройки, не меньше 180 с), если проверен хоть один
  раздел; «🔁 Перепроверить непроверенные разделы» проверяет только
  их и собирает заключение заново. В логе проверки — сколько шёл каждый раздел и с какой попытки он проверен.
  Сообщение о таймауте говорит, что поменять, а не советует снизить max_tokens.
- **«Выключить рассуждения модели»** без привязки к модели: стандартный параметр шаблона чата vLLM и SGLang;
  шлюз, который его отклоняет, получает запрос без него, и MINT это запоминает. Рассуждения MINT замечает по
  ответам (`reasoning_content`, токены рассуждений, `<think>`) и подсказывает выключатель. `llm_extra_body` /
  `LLM_EXTRA_BODY` — свои параметры запроса для любого шлюза.
- **.pdf, .md и .txt** в базе знаний, аудите и контроле исправлений (раньше — только .docx).
  - PDF читается по текстовому слою без моделей (pdfplumber): ничего не скачивается и не покидает компьютер.
    Заголовки — из закладок PDF, иначе со страницы «Содержание» с отточиями, из заголовков слайдов или по размеру
    шрифта; колонтитулы, номера страниц, рамка и штамп ЕСКД, страницы оглавления убираются; таблицы с линиями —
    в Markdown. После загрузки видно, откуда взята структура. Проверено на 13 настоящих PDF (1388 страниц, около
    2 минут): заголовки из закладок — 395 из 398, со страницы «Содержание» — 111 из 114.
  - Скан без текстового слоя и PDF с испорченными шрифтами не индексируются: MINT объясняет почему и что делать.
  - .md: заголовки `#` и таблицы; .txt: нумерованные заголовки и заголовки ЗАГЛАВНЫМИ, UTF-8 / UTF-16 /
    Windows-1251.
  - Примечания Word аудит ставит только в .docx; для других форматов — заключение и лог. В манифест пишутся
    формат документа и источник структуры.
  - Новая зависимость — `pdfplumber` (MIT).
- **Установка без PyTorch.** `requirements.txt` ставит облегчённую сборку Docling `docling-slim[format-docx]`
  (только разбор .docx): без PyTorch, OpenCV и моделей — 66 пакетов и ≈ 0,6 ГБ вместо 114 и 2,1 ГБ; образу Docker
  больше не нужны индекс PyTorch и системные библиотеки OpenCV. На зеркале без `docling-slim` можно по-прежнему
  ставить `docling>=2.0` (`docs/ru/INSTALL.md`). Самопроверка принимает оба варианта.
- **Промпты — данные.** Все тексты для модели теперь в `mint/prompts/ru.yaml` и `en.yaml` — один ключ на текст,
  `{{имя}}` — подстановка, — а не в шести модулях. Тексты перенесены без изменений (запросы к модели в тестах
  совпадают байт-в-байт). `prompts_version()` — язык и хэш набора — пишется в каждую оценку 👍/👎 (в момент
  ответа), в лог аудита и в итоги проверки качества: видно, при каких промптах получен результат.
  `tests/test_prompts.py` проверяет, что на двух языках одни и те же ключи, подстановки и число правил, а формат
  ответа, который разбирает код, в промптах на месте. PyYAML теперь обязателен (он и так был в
  `requirements.txt`).
- **Промпты в интерфейсе** (боковая панель → «📝 Промпты»). Тексты для моделей — чат, уточнение вопроса,
  перефразировка, проверка раздела, самокритика, контроль исправлений, черновик вопросов — правятся на языке
  интерфейса; у каждого — что он делает и что в нём обязательно:
  - «Попробовать в сеансе» — правка действует только в этом окне браузера; «Сохранить» — в `prompts.yaml` рядом с
    программой (`PROMPTS_PATH`), для всех и после перезапуска; «Вернуть умолчание». Хранятся только изменённые
    тексты, так что обновления MINT до остальных доходят; если умолчание изменилось после сохранения правки,
    страница предупредит и покажет разницу;
  - «Проверить правку» применяет её в сеансе и открывает проверку качества с ответами чата на вопросах прошлой
    проверки (каждый — дважды); результат сравнивается с прошлой проверкой ответов;
  - формат ответа, который разбирает код, и подстановки `{{…}}` удалить нельзя: такая правка не применяется (и в
    написанном вручную `prompts.yaml` тоже), страница говорит, чего не хватает. Тексты по умолчанию не менялись;
  - в версию промптов входят и ваши правки; в отзывы, лог аудита и проверки качества пишется и список изменённых
    промптов (`prompts_custom`). Более длинный промпт чата или аудита соответственно уменьшает место под
    фрагменты в окне модели. В Docker правки хранятся в томе с данными (`/data/prompts.yaml`).
- **Русские промпты выровнены с английскими.** Правила, которые были только в английских: отвечать на языке
  вопроса; сохранять язык при уточнении вопроса и перефразировке; цитаты — дословно на языке оригинала,
  пояснения — на языке интерфейса (переведённая цитата не находится в документе, и замечание теряет привязку, а
  исправление — статус «исправлено»). Важно, когда вопрос или документ не на русском, а интерфейс — на русском.
- **Проверка качества: ответы чата.** Каждая ошибка относится к поиску (нужного фрагмента не было в контексте)
  или к модели (ложное «информации нет», нет ссылки на нужный документ, ссылки мимо найденного, ответ на вопрос не
  по базе). «Информации нет» узнаётся по фразе `chat_no_info` из промпта. Каждый вопрос можно задать 1–3 раза. В
  итогах — версия промптов, язык и модель; проверка сравнивается с прошлой проверкой с ответами по вопросам
  (критерий знаков) и показывает, что изменилось в настройках. Фильтр «ответы с ошибками»; в answers.csv — строка
  на каждый ответ. Из консоли: `eval_search.py --answers [--repeat N] [--quick]`.
- **Сценарии — в ядре.** `answer_question()`, `run_audit()` и `verify_remarks()` выполняют ответ чата, аудит
  документа и контроль исправлений без интерфейса; вкладки только рисуют. В настройки отзыва добавлены язык,
  глубина истории чата, справочник сокращений и вес реранкера.
- **Проверка качества в интерфейсе** (боковая панель → «Проверка качества»): поиск проверяется на настоящей
  базе в закрытом контуре без CSV и консоли:
  - MINT составляет вопросы по фрагментам базы (на языке фрагмента) или берёт вопросы прошлой проверки;
    вопросы правятся в таблице, туда же дописываются свои, а вопросы без ответа в базе отмечаются
    «— ответа в базе нет —»;
  - до прогона подсвечивается разметка, которая никогда не засчитается (фразы или раздела нет в документе),
    и показывается фрагмент, по которому составлен вопрос, с выделенным ответом;
  - результаты: hit@K, hit@1, MRR и ложные тревоги с изменениями с прошлой проверки; сравнение конфигураций с
    критерием знаков; рекомендации, которые применяются к сеансу одной кнопкой (и фрагмент для
    `config.yaml`); вопросы, на которых поиск ошибается; отчёты для скачивания. По желанию на каждый вопрос
    отвечает и чат: есть ли ссылка на нужный документ, нет ли ссылок мимо найденного, честный ли отказ;
  - каждая проверка сохраняется в `LOG_DIR/eval/<дата_время>`.
- **Ядро оценки — `mint/evaluation.py`.** `eval_search.py` стал тонкой обёрткой для консоли; язык отчёта — как у
  интерфейса (`MINT_LANG` или `--lang`). Повторные запросы к сервисам внутри прогона кэшируются на время прогона
  (`services.request_cache`) вместо подмены функций сервисов.
- **Интерфейс.** Своё оформление и движение там, где оно показывает, что произошло:
  - шапка один раз прорисовывается при загрузке; тонкая линия вверху движется, пока MINT работает;
  - аудит и контроль исправлений открываются штампом заключения («Требует доработки», «Есть замечания»,
    «Согласовано», «Всё исправлено») и счётчиками по критичности или статусам;
  - чат: ваш вопрос справа, ответ — карточкой, источники — нумерованным списком (документ › раздел, баллы
    ниже), в пустом чате — список документов базы;
  - шрифты (Onest, Unbounded — OFL) раздаёт сам Streamlit из `static/` (`enableStaticServing` в
    `.streamlit/config.toml`): из интернета ничего не загружается. При запуске из другой папки — системные
    шрифты;
  - при `prefers-reduced-motion` движение отключается; страница работает и на телефоне.
- **Проверка ссылок в чате.** Каждая ссылка `[Источник: файл, раздел]` в ответе сверяется с фрагментами, которые
  модель реально получила: файл должен быть среди источников, раздел — среди заголовков этого файла. Ссылки мимо
  контекста помечаются ⚠️ и перечисляются в предупреждении под ответом (обычно они указывают на додуманное
  утверждение). Без лишнего вызова модели; неверные ссылки сохраняются и в отзыве 👍/👎.
- **Склейка соседних фрагментов.** Если поиск нашёл соседние фрагменты одного документа, модель получает их
  одним блоком в порядке текста, без повтора перекрытия. Блоки по-прежнему идут по релевантности. Работает и на
  уже собранных базах.
- **Обрезка вокруг найденного места.** Фрагмент длиннее лимита контекста обрезается вокруг найденного места
  (child из векторного поиска или самое плотное по словам вопроса место), а не с начала; ближайший заголовок
  выше окна сохраняется, чтобы раздел в ссылке был верным. У таблиц остаются название и шапка. Раньше найденный
  текст в конце длинного фрагмента терялся.

- **Нарезка на фрагменты.** Фрагмент режется сначала по границе абзаца, затем строки, предложения и только потом
  слова (раньше разрез почти всегда приходился на последний пробел — посреди предложения). Заголовок больше не
  остаётся в конце фрагмента отдельно от своего текста, перекрытие начинается с целого слова. Действует на
  документы, проиндексированные после обновления, — для уже загруженных переиндексируйте базу.
- **Обрезка фрагмента.** Фрагмент, начинающийся со строки заголовка и длинного абзаца без точек, обрезался до
  одного заголовка; теперь сохраняется не меньше половины лимита.
- **Разделы аудита и контроля исправлений.** Абзац длиннее размера раздела (обычно большая таблица) делится —
  таблица по строкам с повтором шапки — а не становится одним разделом в несколько раз больше лимита, который
  не помещался в окно модели. Заголовок в конце раздела переносится в следующий — вместе со своим текстом.
- **Эмбеддинги (защита).** Векторы из пакетного ответа сопоставляются с текстами по полю `index`
  OpenAI-совместимого API, а не по положению в ответе. Распространённые серверы порядок сохраняют; это защита от
  шлюзов, которые его меняют.
- **Сокращения.** Поиск работает и в обратную сторону: вопрос с полной формой («средства защиты информации»)
  находит фрагменты, где есть только сокращение.
- **Контроль исправлений (защита).** Если модель вместо одного из заданных статусов ответила «исправлено
  частично», это показывается как частичное исправление, а не как исправленное.
- **Отчёт оценки поиска** (`eval_search.py`).
  - В `details.csv` нет пустых ячеек: у вопросов без ответа в базе в колонках «Место» — сработал ли сигнал
    «уверенность низкая»; вместо пустого балла реранкера — причина; «> 10» — правильный фрагмент не найден.
    Новые колонки: доля слов вопроса в контексте и согласие dense с BM25.
  - Раздел «Где конфигурации расходятся»: текущая конфигурация против лучшей, простого гибрида и одного
    векторного поиска — по вопросам, с p по критерию знаков: может ли разница быть случайной. Заменяет грубое
    правило «10 % вопросов».
  - Раздел «Вопросы без ответа в базе»: сработал ли сигнал, лучший балл реранкера, что найдено.
  - Нет повторяющейся колонки при `top_k` = 3.
  - Черновик вопросов (`--generate`): если модель пересказала цитату, берётся ближайшее предложение фрагмента —
    колонка `contains` заполняется чаще.
- **Подписи источников.** Источник в чате, аудите и отчёте оценки подписан разделом, где найдено место, а не
  разделом, с которого начинается фрагмент (фрагмент часто захватывает несколько разделов).
- **Схемы.** `docs/MINT_architecture` и `docs/MINT_engineering` приведены к 20.1 и изменениям выше (языки,
  отзывы, склейка и обрезка фрагментов, проверка ссылок, правило уверенности, нарезка, английский стеммер).
  Теперь они собираются скриптами `tools/diagrams/`, а `tests/test_diagrams.py` проверяет, что они не отстают от
  кода. Картинки-превью пересобраны (на них ещё была версия 19.1).
- **Схемы на английском.** В `docs/MINT_architecture` и `docs/MINT_engineering` теперь английские версии,
  русские переехали в `docs/ru/`. Обе собираются одними скриптами (`--lang en`, переводы — в
  `tools/diagrams/en.py`), поэтому не разойдутся.
- **Сигнал «уверенность низкая».** С реранкером сигнал теперь зависит только от его лучшего балла
  (`low_conf_rerank`). Раньше дополнительно требовалось, чтобы слов вопроса в контексте было мало, а dense и
  BM25 не сошлись. Но на вопросах, ответа на которые в базе нет, слова темы обычно есть, поэтому сигнал почти не
  срабатывал, даже когда реранкер оценивал все фрагменты низко. Без реранкера правило прежнее.
  `weight_rerank: 0` оставляет порядок как у гибрида, а реранкер по-прежнему решает, ставить ли сигнал.
  `eval_search.py` подбирает пороги по тому же правилу и предлагает `weight_rerank: 0`, если гибрид без
  реранкера ранжирует лучше.

- **Английские промпты.**
  - Отдельные английские версии промптов.
  - В чате модель отвечает на языке вопроса.

  - Индекс BM25 пересоберётся автоматически при первом поиске.
- **«Символов на токен».** «Определить у сервера» измеряет значение на языке базы знаний: для русской базы —
  на русском тексте (как раньше), для английской — на английском, поэтому фрагменты английских документов не
  урезаются. Для смешанной или пустой базы измеряет на обоих языках и берёт меньшее — размеры фрагментов
  безопасны для любого из них. Язык базы определяется по буквам в её тексте.
- **Тесты.**
  - `tests/test_i18n.py`: полнота перевода, английские промпты и разбор ответов, английский поиск, английский
    интерфейс целиком.
  - Смоук-тест страницы переключает язык на настоящем Streamlit.

## 19.3

- Новое название.
- Аудит рассчитан на любые документы на согласование, а не только на ТЗ.
- Поле «🎯 Особое внимание»:
  - модель проверяет эти пункты в первую очередь;
  - самокритика не удаляет замечания по ним без опровержения;
  - нормы по ним один раз ищутся в базе и добавляются к каждому разделу.
- Заключение и лог разделов не пропадают после скачивания файлов.
- Лог проверки скачивается отдельно: настройки прогона, источники норм и отклонённое самокритикой по
  каждому разделу.
- Свой `glossary.json`:
  - пустое значение убирает ошибочную расшифровку, найденную в документах;
  - файл читается и в Windows-1251.

## 19.2

- `.env` читается и без пакета python-dotenv, в UTF-8 (с BOM или без) и Windows-1251.
- Пустая системная переменная больше не перекрывает значение из `.env`.
- Панель показывает, какой `.env` прочитан или где MINT его искал. При ошибке подключения — причина:
  ключ, адрес, сертификат, нет соединения.
- Ответы серверов перепроверяются сразу после исправления ключа или сертификата.

## 19.1

- Чат учитывает историю: уточняющий вопрос («а для второго контура?») переписывается в самостоятельный.
- Рассуждения моделей (`<think>`) убираются из ответов; обрезанный ответ помечается.
- Ссылки указывают раздел внутри фрагмента, а не только первый.
- Вопросительные слова («сколько», «чем») не участвуют в поиске.
- Частичный сбой реранкера не искажает порядок.

## 19.0

- Реранкер оценивает всех кандидатов (а не первые 6) и получает самую релевантную часть каждого документа:
  найденный векторным поиском фрагмент или окно с наибольшей плотностью слов запроса. Если кандидаты не
  помещаются в один запрос к шлюзу, отправляется несколько запросов.
- Векторный поиск и реранкер получают исходный вопрос. Слова расширения («определение», «состав» …)
  добавляются только в BM25 и с малым весом; буст точной фразы ищет предмет вопроса.
- Префикс-инструкция для модели эмбеддингов подбирается по её имени (Qwen3-Embedding, e5, FRIDA …).
  Векторы нормируются — поиск идёт по косинусу.
- Аудит:
  - самокритика возвращает категорию и дословную цитату;
  - в «Документе с замечаниями» каждое замечание привязано к одному месту и добавлено примечанием
    Word — текст документа не меняется.
- Запись в базу защищена блокировкой. BM25 для длинных запросов (аудит) работает в десятки раз быстрее.

## Переход с v17

- База v17 открывается как есть. При первом поиске BM25-индекс пересоберётся (теперь с учётом русской
  морфологии), сокращения соберутся из документов.
- Старый `glossary.json` читается (`rerank_abbreviations` и `bm25_expansions`). Новый формат проще:
  `{"СЗИ": "средства защиты информации"}`.
- Документы, загруженные в v17, помечены «ℹ️ загружен до v18»: их оригиналы не сохранены, поэтому для
  переиндексации их нужно загрузить заново.
- Переменные окружения v17 (`LLM_API_URL`, `EMBED_API_URL`, `RERANK_API_URL`, `LLM_API_KEY`, `KB_DIR`,
  `CA_BUNDLE_PATH`, `SSL_INSECURE`, `GLOSSARY_PATH`, `DEFAULT_LLM_MODEL`) работают без изменений.
