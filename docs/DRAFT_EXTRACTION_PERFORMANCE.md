# Ускорение разбора оснований Word (PR #23)

Этап извлечения существенных требований из исходных документов теперь может делать несколько независимых запросов к LLM одновременно. Порядок результатов и ID `R1…` сохраняется; уже проверенные фрагменты читаются из существующего локального кэша. Повторный запуск после сбоя обрабатывает только незавершённые/невалидные фрагменты.

Настройка в `config.yaml` (не добавляет новых полей в интерфейс):

    draft_extract_parallel: 2

По умолчанию — **2**. Допустимо **1** (прежний последовательный режим), до **4** активных запросов максимум. Большее значение программно ограничивается четырьмя. Шлюз может ответить 429 или замедлиться; если такое происходит, поставьте 1. Скорость зависит от шлюза, ограничений и доли уже закэшированных фрагментов.

**Что замерять на тех же документах:** общее время формирования, LLM-вызовы и суммарное время этапа «Разбор оснований», число фрагментов, процент извлечённых требований, итоговую ручную оценку черновика. Суммарное время LLM-запросов при параллельной работе может превышать реальное время этапа — это нормально, запросы перекрываются.

Запуск синтетического контрольного теста без сети:

    python tests/test_draft_parallel.py

Тест имитирует одинаковую задержку, проверяет ускорение, стабильный порядок ID/содержания, контрольные точки, ошибки и потокобезопасный сбор метрик. **Он не доказывает ускорение рабочего шлюза и не гарантирует отсутствие потери качества.** Проверку на реальном комплекте и размеченных требованиях проводим отдельно после слияния.
